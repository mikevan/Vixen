# Bounded live signature analysis: MVP beta

Vixen preserves relevant Hunter evidence and interprets a supported sequence soon enough to support a timely human decision. The source, application and model remain fixed throughout a field run.

## Ordinary workflow

The foreground connection service receives normal Hunter records. A separate bounded worker selects deauth/EAPOL observations sharing an observed transmitter identifier and a structured Remote ID observation from one producer/session. It preserves an immutable assessment input, then invokes the offline model automatically. Collection never awaits inference. There are no scenario controls or harness-name branches in the application.

Optional GET_TEXT observation timing supplies source first/last uptime. The selector calculates ordering and window membership, including 32-bit uptime wrap; absent source time stays unknown. Receipt time is not substituted for RF time. Remote ID detail preserves the original service-data bytes. Multiple reports from one source are not independent corroboration.

The model selects one of seven evidence-pattern interpretations. Procedural code retains references, calculates exact intervals and renders the concise finding. An evidence guard rejects unsupported proposals without repairing them or counting rejection as a semantic pass. The model does not generate an evacuation instruction, establish causation, or authenticate an aircraft. Deauth/EAPOL/Remote ID observations alone do not prove the separate Wi-Fi/BLE-outage evacuation policy.

Ops shows progress and the accepted assessment. Normal background notifications follow permission and sleep settings. Saved assessments retain the immutable input, raw model output, model identity and result. Duplicate completed inputs restore their assessment; pending or failed inference does not stop monitoring. New assessments do not erase the previous completed finding while inference is pending.

## Running and observing the field test

Use the [Hunter-TestHarness operator instructions](https://github.com/mikevan/Hunter-TestHarness#run-it-yourself). Enable Deauth, EAPOL and Remote ID, keeping trackers off. The source emits the three stages after 20, 32 and 50 seconds; the operator starts it. The application automatically analyzes the evidence and monitoring continues after the 61-second input completes.

The owner explicitly approved a separate Android qualification package. Its inputs and results are quarantined outside field collections, with no product controls or model-visible simulation flag. Remove that package before the operator's field run. Freeze the application, model and firmware hashes; do not intervene to create a successful result.

Compare the normal field journal, saved assessment and source SD/PCAP evidence. Record missing packets, rejected answers, timeouts and delivery failures. Synthetic source observations validate the live product integration; they do not validate RF reception, a real outage, drone intent, source independence or evacuation effectiveness.

## Saved reports and plain language (build 142)

The normal AI panel opens **AI reports**. Saved assessments display the original
analysis completion date and time (phone local time), a stable report ID and
Hunter session. UI refreshes and file modification times do not create a new
report time. Legacy records without that field show "Creation time unavailable".
Pending or failed assessments remain visible with their actual status.

Open a report to **Archive report**, **Restore from archive**, or **Export report**.
Export uses Android's save-file picker and preserves the original JSON, including
model identity, input, source references, raw output and result. Packet files
are separate and are not included in this export. Archive markers live separately
from the assessment files. Repeating Archive or Restore does not edit or delete
reports, rerun inference, reset notification suppression or change capture.
Archived reports still participate in the existing assessment cache.

The user-facing sensor label is **Drone**. Reports describe the drone
identification broadcast and the detected sequence in plain language. Specific
evidence gaps or conflicting timing remain explicit; generic warnings are not
repeated in every report.
Technical evidence retains Remote ID terminology and original bytes. Older saved
reports use the clearer wording when displayed; exported originals stay intact.

This is a normal product feature. The completed T1 result belongs to frozen
build 141; future tests must record the actual new build number.


## OPS current report and AI Reports page (build 143)

OPS has one dedicated current-report panel. Archive opens a confirmation with
Cancel and Archive. Confirming removes that report from OPS; an older report is
not promoted into its place, including after restarting the application. A new
assessment can populate the panel. Restore makes a report active again, but an
older restored report does not replace the newest assessment.

The navigation's Reports tab opens the AI Reports page, with Active and Archived
history, newest first. Each assessment retains its completion time, stable ID,
Hunter session and original status. Report details provide Export and Restore;
archiving from history requires the same confirmation as OPS.

Archive changes only separate presentation metadata. It never deletes reports,
packet captures, field journals, card imports or source records, and does not
trigger inference or change notification deduplication. The original reports and
raw outputs stay byte-identical. JSON export includes the report; packet files
and journals remain separate on the phone and in the preserved test backups.

New assessments also retain application version, the system prompt, output
schema and grammar, output budget and timeout, model hash/version, prepared
model input, raw model response, source identifiers, counts and source-clock
first/last timestamps. These support later comparison with preserved captures
and journals. Existing reports are not rewritten to invent missing metadata.
This metadata is written by the existing background analysis worker, not BLE
callbacks. The model input, prompt and inference settings are unchanged.


## Report window styling (build 144)

The OPS report and report-history entries reuse Vixen's instrument housings,
cyan headings, dark glass and recessed action controls. Report dialogs use the
same colors and enclosed edges. Shared page and Builder-modal back controls are
inset inside the housing, with content kept clear of them; the controls have a
closed outline rather than extending into the outer rail. Navigation, archive
confirmation, inference and stored evidence behavior are unchanged.


## Single-frame pages (build 145)

The added outer route housing and its top/bottom control bands were removed.
Back is part of the existing content frame on Mission, Events, Tools, Builder,
System and AI Reports. AI Reports uses one frame with divided history entries,
not a second set of framed cards inside another housing. The OPS current report
retains its single housing. Navigation and data retention are unchanged.


## Inset Back housing (build 146)

The upper-left Back control sits inside a small recessed housing that reuses
the content frame's artwork. It occupies the existing header row; no outer page
frame or lower navigation band is added. Report and evidence retention are
unchanged.


## Border-integrated Back (build 147)

Back is now drawn by the content housing as a return in its upper-left border.
The inner return joins the existing top and left rails; there is no nested
Back housing. The click target occupies that border inset and the existing
heading leaves room beside it. No additional page frame or control row is added.
